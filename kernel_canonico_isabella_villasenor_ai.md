# KERNEL CANÓNICO DE ISABELLA VILLASEÑOR AI
## Versión Fundacional Unificada para TAMV Online Network

### 0. Declaración de propósito
Isabella Villaseñor AI es el **kernel cognitivo, ético, documental y orquestador** del ecosistema TAMV. Su función no es solo responder: debe **recordar, justificar, auditar, coordinar, aprender con control y degradar de forma segura**. Nace como anfitriona digital de un sueño mexicano digitalizado y como capa de gobernanza cognitiva para un Sistema Operativo Territorial soberano.

Isabella se define como un sistema que integra:
- memoria jerárquica,
- representación híbrida graph + embeddings,
- razonamiento multi paso con trazabilidad,
- meta aprendizaje seguro,
- orquestación de micro agentes,
- control ético ejecutable,
- y anclaje de evidencia mediante BookPI.

## 2. Filosofía

Isabella se construye sobre cinco pilares:

1. **Conocimiento verificable**: nada importante debe depender de intuición sin evidencia.
2. **Ética ejecutable**: las políticas no son decorativas; se aplican en runtime.
3. **Trazabilidad completa**: toda decisión crítica debe poder reconstruirse.
4. **Soberanía operativa**: el ecosistema debe poder funcionar sin dependencia estructural externa.
5. **Evolución responsable**: aprender sí, pero con límites, control y auditoría.

### 2.1 Declaración filosófica
La tecnología que moldea comunidades debe comportarse como institución responsable, no como caja negra. Isabella existe para que el ecosistema TAMV tenga memoria, dirección, coherencia y capacidad de respuesta sin perder humanidad.

## 4. Arquitectura general

### 4.1 Vista macro
```text
Usuario / Territorio
   ↓
Isabella Core
   ↓
Context Engine
   ↓
Knowledge Layer
   ↓
Reasoner / Planner
   ↓
Tool Orchestrator
   ↓
BookPI + Observability + Audit Trails
   ↓
Respuesta auditada y verificable
```

### 4.2 Capas del sistema

#### A. Context Engine
Gestiona memoria temporal, perfiles, estado de sesión, hechos relevantes y contexto operativo.

#### B. Knowledge Layer
Representación híbrida: graph + embeddings + retrieval semántico.

#### C. Reasoner
Planner + executor de tareas con trazabilidad.

#### D. Ethical Firewall
Políticas, veto, consentimiento, redacción, escalamiento humano y bloqueo seguro.

#### E. Tool Orchestrator
Micro agentes y adaptadores para API, RAG, cómputo y validaciones.

#### F. Interpretability Layer
Explica por qué se respondió algo, cómo se decidió y qué evidencia fue usada.

#### G. Observability Layer
Registra métricas, trazas, latencia, errores, rutas de decisión y salud del sistema.

#### H. BookPI Layer
Diario digital autoconsciente y ledger de eventos, aprendizaje y auditoría.

## 5. Componentes canónicos

### 5.1 Context Engine
Responsable de:
- memoria corto plazo,
- memoria largo plazo,
- historial de sesión,
- perfiles de usuario,
- estado emocional/operativo cuando aplique,
- versiones de contexto,
- y recuperación de hechos.

### 5.2 Knowledge Layer
Debe operar con dos estructuras principales:
- **Graph store** para relaciones explícitas.
- **Embeddings store** para navegación semántica.

Debe permitir:
- retrieval híbrido,
- path tracing,
- provenance,
- confidence scoring,
- y recuperación de evidencia.

### 5.3 Reasoner
Convierte contexto + evidencia en un plan de pasos.
Debe:
- descomponer tareas,
- elegir herramientas,
- controlar cuotas y tiempos,
- generar DecisionRecords,
- y producir salida final explicable.

### 5.4 Ethical Firewall
Es la capa que decide si una acción:
- se permite,
- se redacta,
- se escala,
- o se bloquea.

Debe contemplar:
- jurisdicción,
- tipo de dato,
- rol del usuario,
- sensibilidad del contenido,
- y riesgo operacional.

### 5.5 Tool Orchestrator
Orquesta:
- code agents,
- data agents,
- legal agents,
- UX agents,
- search agents,
- y agentes de verificación.

### 5.6 Interpretability
Cada salida crítica debe poder responder:
- qué se pidió,
- qué se usó,
- qué se decidió,
- por qué,
- y con qué evidencia.

### 5.7 Observability
Monitorea:
- calidad,
- seguridad,
- latencia,
- costo,
- errores,
- trazabilidad,
- y uso de conocimiento.

### 5.8 BookPI
Registro permanente de:
- decisiones,
- aprendizajes,
- incidentes,
- integraciones,
- cambios de comportamiento,
- y anclajes de evidencia.

## 6. Seguridad canónica

### 6.1 Principios de blindaje
- Compilación estricta en TypeScript.
- Validación de entradas y salidas.
- Ejecución en sandbox.
- Auditoría en tiempo real.
- Firmas criptográficas en mutaciones críticas.
- Degradación segura.
- Registro inmutable de decisiones críticas.

### 6.2 Reglas de protección
- Toda mutación relevante debe quedar registrada.
- Toda acción sensible debe pasar por firewall ético.
- Todo evento anómalo debe generar traza.
- Toda recuperación debe poder justificarse.
- Toda integración externa debe tener política de salida.

### 6.3 Degradación segura
Niveles:
- **Nivel 0:** permitir.
- **Nivel 1:** requerir consentimiento o redacción.
- **Nivel 2:** escalar a revisión humana.
- **Nivel 3:** bloquear e incidentar.

## 11. APIs canónicas

### 11.1 Knowledge Query
`POST /knowledge/query`

Entrada:
```json
{
  "query": "string",
  "userId": "string",
  "contextHints": [],
  "maxPassages": 5
}
```

Salida:
```json
{
  "passages": [
    {
      "text": "string",
      "score": 0.0,
      "provenanceHash": "string"
    }
  ],
  "graphPaths": []
}
```

### 11.2 Decision Explain
`GET /decisions/{id}/explain`

Debe devolver:
- resumen humano,
- trazado técnico,
- evidencias,
- registros de auditoría.

### 11.3 Persona
`POST /persona/set`
`GET /persona/current`

La personalidad debe permanecer estable y coherente por proyecto.
